# VOTC 进化机制 / 链路参考

> 从 VoiceOfTheCommunity 1.1.5 反编译整理，用于天命骨头·重构的进化设计参考。
> 机制部分均对照了实际代码；链路表区分「已确认」与「推测」。

## 一、三种进化机制对比

| | 神品合成 (Masterpiece) | 骨头升级 (BoneUpgrade) | 运行时替换 (自定义) |
|---|---|---|---|
| 触发方 | 游戏原生系统 | 游戏原生系统 | 自己写的 Ability / MonoBehaviour |
| 注册位置 | `Masterpiece.Initialize` 前缀，往 `_enhancementMaps` 追加 | `SuperAbility.CreateInstance` 前缀，往 `_enhancementMaps` 追加 | 无需注册，代码里直接换 |
| 道具要求 | 必须有一个刻印是 `Masterpiece`(29) | 不占刻印位 | 不占刻印位 |
| 命名约定 | `X` ↔ `X_2`（可链式 `_3`） | `X` ↔ `X_BoneUpgrade` | 任意 |
| 触发条件 | 由游戏判定（收集/合成规则） | 由游戏的骨头强化流程判定 | 完全自定义 |
| 写代码量 | 0（只加数据） | 0（只加数据） | 中等（要写条件检测 + 替换） |
| 代价 | 吃掉一个刻印位 | 依赖玩家能拿到升级手段 | 无额外代价 |

### 注册代码长什么样

```csharp
// 神品：X + X_2
new EnhancementMap {
    _from = new AssetReference(items["X"].guid),
    _to   = new AssetReference(items["X_2"].guid)
};

// 骨头升级：X + X_BoneUpgrade
new EnhancementMap {
    _from = new AssetReference(items["X"].guid),
    _to   = new AssetReference(items["X_BoneUpgrade"].guid)
};
```

### 运行时替换的核心三行

```csharp
ItemReference target;
if (GearResource.instance.TryGetItemReferenceByName(item.name + "_2", out target))
{
    var req = target.LoadAsync();
    req.WaitForCompletion();                      // 必须等资源加载完
    if (item.state == Gear.State.Equipped)        // 只有装备中/在背包才换
        item.ChangeOnInventory(
            Singleton<Service>.Instance.levelManager.DropItem(req, Vector3.zero));
}
```

`ChangeOnInventory` 是原地替换，位置、强化等级上下文都保留，玩家看不到"掉落再捡"的过程。

## 三、给「天命骨头·重构」的三个方案

前提：你的道具两个刻印都锁死成 `Bone`，**神品方案（机制 1）直接用不了**——它要求占一个 `Masterpiece` 刻印位。

### 方案 A：骨头升级（最省事，零代码）

- 再做一个 `Custom-DestinyBone_BoneUpgrade` 道具，注册 `EnhancementMap`
- 优点：完全走游戏原生流程，不用写条件检测
- 缺点：**触发权在游戏手里**——玩家得有能升级骨头的道具/事件，你不能指定"打 100 次触发"

### 方案 B：运行时替换（最自由，推荐）

- 自己写计数器和替换（上面那三行代码）
- 条件随便定，比如：
  - 累计触发 200 次负面状态 → 进化
  - 单局内叠满 5 层「刻印 +2」→ 进化
  - 持有另一件骨头系道具时进化
  - 血量低于 20% 时进化（危险流）
- 优点：不占刻印位、条件完全自定义、可逆可加视觉反馈
- 缺点：要写 1 个 Ability + 1 个进化后道具（可复用现有骨架）

### 方案 C：双段进化（B + 再进化）

`天命骨头·重构` → `_2`（条件 A）→ `_3`（条件 B），像灵巧的手那条三连链。
代价是要多做两个道具定义，但代码结构完全一样。

### 我的建议

选 **方案 B**，条件用「累计触发 200 次负面状态」——和道具本身"攻击附带 6 种状态"的设计闭环，玩家会主动去堆攻速把进化打出来，而不是靠运气。

进化后的版本可以把：
- 负面状态概率从 25% 提到 35%
- 刻印 +2 提到 +3
- 属性从 +25% 提到 +30%

这样两个版本有明确的强度阶梯，不会变成"进化完就没意思了"。

# 附：每个运行时进化的具体要求（源码级）

| 道具 | 计数方式 | 判定条件 | 阈值 | 备注 |
|---|---|---|---|---|
| 纳垢圣杯 → 女神圣杯 | `onGiveDamage` | 只要 **替换(Swap)技能** 造成的伤害实例（`MotionType = 6`），命中即 +1 | **150 次** | 不看伤害量、不看暴击；打小怪也算 |
| 冻魂 → 寒魄 | `onGaveStatus` | 只有 **冰冻（Kind=1）且施加成功** | **250 次** | 被免疫/失败不计；其他状态不计 |
| 制式矿镐 → 传说金镐 | `Currency.onEarn` + 每帧查精华 | ① 累计获得金币 ≥ 1500 ② 或装备的精华名为 `Dwarf` / `KingDwarf` | 1500 金币 | 两条任一满足即进化 |
| 空虚容器 → 欲孽之心 | 每帧 `Update` | 已装备精华里存在 `Succubus`（魅魔） | 即时 | 代码取随机一个精华判断，等价"持有魅魔" |
| 银河弹弓 ↔ 甲斗 | `Inventory.onChanged` | 背包里同时有 `VeiledMask`（掩饰的面具） | 即时 | **双向**：两件一起进化；失去面具则甲斗退化 |
| 小树枝 → SmallTwig_2 | `weapon.onSwap` / `weapon.onChanged` | 当前头骨是 `Skul` 或 `HeroSkul`（初始骨） | 即时 | 换骨时判定 |
| 萎哥 ↔ 薛定谔的药物 | 定时器 | 同一件道具在两个形态间切换 buff | 定时 | **不是换道具**，别被描述误导 |
| 毒月剑 / 黎明长枪 | — | 无任何代码引用 `_2` | — | 只有道具定义，**进化没接** |
| 天命骨头 → 永恒骨头：天命 | 骨头升级系统 | `SuperAbility._enhancementMaps` | — | 走游戏原生骨头强化 |

## 三种计数写法的取舍

1. **事件计数**（`onGiveDamage` / `onGaveStatus`）——最稳，只在事件发生时 +1，不受帧率影响；缺点是只能数"你能挂上钩的事件"
2. **背包变化**（`Inventory.onChanged`）——适合"持有某件东西"类条件，但要注意自身替换道具时也会触发，得防递归
3. **每帧检查**（`Update`）——最灵活也最容易出性能/重复触发问题，VOTC 自己只在简单条件上用

## 对四档骨头链的候选条件

| 条件 | 实现难度 | 手感 | 与现有设计的契合度 |
|---|---|---|---|
| 累计击杀（当前） | 已实现 | 平滑 | 中，和"属性叠加"没有主题关联 |
| 累计命中次数 | 低（`onGiveDamage` +1） | 平滑，堆攻速更爽 | 高，和"攻击上状态"同源 |
| 持有某件联动道具 | 中（要再做一件道具） | 有探索感 | 高，可以做"人魂+地魄"合成天命之类 |
| 使用初始骨 | 低（`weapon.onSwap`） | 有构筑限制，很"骨头" | 很高，但会逼玩家不能换骷髅 |
